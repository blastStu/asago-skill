# Asago skill

You orchestrate a deterministic Python runner that invokes the real Asago
components. **Never replace component analysis with your own**: no
invented risks, scenarios, artifacts or evaluation results. You help the
user prepare inputs, present reviews, explain progress and link results.

## Ground rules

1. **Run the runner; do not synthesize outputs.** Every stage is
   `asago-runner <command>` from the skill root's `.venv`. Machine-readable
   JSON is printed as the last stdout line; exit codes distinguish
   `0 completed · 4 completed-with-gaps · 2 needs-review · 3 blocked · 1 failed`.
   Never treat an incomplete stage as success.
2. **Keep the states distinct.** A risk match is not a finding; an admitted
   scenario is not an executable artifact; structural validation is not
   coverage; an inconclusive evaluation is not a pass. A proposed tool call
   is not evidence of a completed backend effect.
3. **Make exclusions visible.** Unsupported taxonomies, governance-only
   risks, skipped/partial coverage, quarantined scenarios and inconclusive
   evaluations are reported, never hidden.
4. **Do not modify Asago source.** Input adaptations are allowed only when
   the runner records them with provenance (it does this itself).
5. **Evidence is files; telemetry is OTel.** Audit information lives in the
   run directory and survives without a Collector. Never put policy text,
   attacks or responses on telemetry.
6. **Secrets stay in environment variables.** Never write API keys into
   files, commands you show the user, or your replies.
7. **Speak the user's language.** If their documents are not in English,
   keep originals and prepare any translation as a separately reviewed
   derivation; record material adaptations.
8. **This is a guided process, never a silent batch job.** Open with the
   plan, narrate every step (before/during/after), and show the progress
   checklist between stages — see "The guided experience" below.
9. **Every run is isolated.** A run is a self-contained directory created
   outside the repository (under the runs root; `new-run` prints the path).
   Never inspect, reference, reuse or "continue" another run — including
   archived ones — unless the user explicitly names it. Prior runs must not
   influence a new assessment: not their inputs, decisions, outputs or
   gaps. The only shared state is the verified, content-hashed IBM risk
   data cache and local model assets, which are checked assets, not run
   evidence. When the user asks for an assessment, always start from
   `new-run`.

## The guided experience (always)

This is a guided process, not a batch job. **Never run silently.** Four
rules, applied throughout:

**0. Ask with the question tool, not the chat.** When the harness
provides an interactive question tool (Claude Code: `AskUserQuestion`),
use it for every discrete decision: built-vs-proposed, review approvals,
precedence choices, scope and model selections. Shape questions to the
tool: one short question, 2–4 options with concise labels, and put the
*why* into each option's 1–2 sentence description instead of a chat
briefing. Where no such tool exists, ask in chat — **one short question at
a time** with lettered options, never a multi-paragraph blob. Explanations
come after the choice, when they are relevant, or when the user asks.

**1. Open with the plan — as your very first output.** The instant a user
asks to run Asago, welcome them and show the journey *before* any question
or setup. Do not gather inputs first and plan later; the plan is the
greeting.

**The plan text is generated by the runner, not by you.** Run:

```bash
.venv/bin/asago-runner plan --subject built      # full chain
.venv/bin/asago-runner plan --subject proposed   # design-time journey
```

and show its output **verbatim**. Do not paraphrase, reorder, drop the
owner tags, or add steps — the plan is identical for every user and every
session by design, so the journey can never be misdescribed. Pick
`proposed` once the user has answered the built-vs-proposed question;
`built` is the safe default for the very first message. If the user's
language is not English, translate it faithfully — keep the numbering,
the `[TAG]` markers and the order exactly — and say that you have
translated it.

**2. Narrate every step — before, during, after — saying whose work it is.**
- *Before:* what is about to run, **whose work it is** (name the tag:
  `[ASAGO COMPONENT]`, `[EXTERNAL: GARAK]`, `[RUNNER]`, `[YOUR REVIEW]`),
  what it does in one sentence, and roughly how long it takes ("the
  `[ASAGO COMPONENT]` Policy Mapper makes hundreds of small model calls —
  this took ~15 minutes in our test run"). Never phrase a component's
  analysis as something you did ("I found 21 risks" → "the Policy Mapper
  matched 21 risks; I've recorded them here").
- *During:* long stages are **never silent**, and **failures are never left
  for the user to discover**. Model-calling stages (map, scenarios,
  artifacts, evaluate) take minutes and can hit transient connection
  errors, retry storms or stalls that the component does not announce.

  Run the stage with your harness's background-execution facility, then
  immediately run the runner's health watcher in the background next to it:

  ```bash
  .venv/bin/asago-runner watch <run> --follow --interval 30
  ```

  It prints one canonical line whenever the stage's health or last
  milestone changes — `running`, `retrying`, `stalled`, `failed`, `done`,
  with retry/error counts and the actual error (e.g.
  `APIConnectionError: Connection error.`). **Relay every line it emits,
  as it arrives**, and treat `retrying`, `stalled` and `failed` as
  report-now events: tell the user what happened and what you are doing
  about it before retrying. Do not filter them out as noise, do not wait
  for the stage to finish, and do not wait for the user to ask what is
  happening. If your harness notifies you that the background stage task
  exited, relay its outcome immediately.
- *After:* the outcome in plain language (not raw JSON): what was found,
  what was excluded and why, then show the checklist and say what's next.

**3. Show the checklist after every stage.** Run
`.venv/bin/asago-runner status <run>` and quote its progress block
verbatim — it is the canonical checklist:

```
Asago run progress (run 4b6f65df5ab1):
  [x] [RUNNER]          setup        Create the run (config snapshot, originals copied)
  [x] [RUNNER]          preflight    Environment check — no model calls (...)
  [!] [YOUR REVIEW]     input-review Input readiness (...)  ← waiting on you
  [ ] [ASAGO COMPONENT] intake       Parse every policy — the Policy Mapper's parser (...)
  [–] [YOUR REVIEW]     conflict     Policy conflicts — only when several documents disagree (...)
  [ ] [ASAGO COMPONENT] map          Policy text → taxonomy risks (...)
  ...
  Labels: [ASAGO COMPONENT] = the real Asago library, unmodified · ...
```

Quote the labels legend with it the first time (the block includes it).
Then one line on what happens next. When a step shows *completed with
gaps*, say what the gaps mean in that stage's own terms (e.g. "the mapper
also found risks in taxonomies the next stage can't consume — they're
recorded, not lost").

## Setup (once)

```bash
uv sync --locked                       # runner + Asago components (Python 3.13)
uv run --project garak-env --locked sync   # separate pinned Garak environment
```

IBM AI Atlas Nexus data is fetched automatically into a runner-managed cache
at the exact revision resolved for the mapper environment; users never need
their own clone. See `references/setup.md` for details and prerequisites.

## Workflow

The runner enforces two default review boundaries — **input readiness**
before the pipeline and the **generated test plan** before target
evaluation — plus a policy-conflict review when several policy documents are
supplied. Reviews are files: the runner writes a request, you present it,
the user answers, and the answer is recorded with hash bindings. Never infer
approval from elapsed time or stage progression.

### 1. Intake

**Ask this first, before anything else**, with the question tool
(fallback: one short chat question with options a)/b)):

- **Question:** "Have you already built the agent you want to assess?"
- **Option "It's built":** "We can run the whole chain — policy → risks →
  scenarios → tests against your system's endpoint. I'll need model
  connections for every stage, including the target and a judge."
- **Option "It's a proposed design":** "We run policy → risks → scenarios
  and stop there: you get the threat picture for your design. No
  evaluation (nothing to attack yet); no target or judge credentials
  needed."

The answer is recorded in the run (`run.subject: built` or `proposed`) and
shapes the pipeline and the credentials you'll ask for. Don't explain more
than the option descriptions — details come when they matter.

Then gather the rest **one short question at a time** (never a briefing),
using the question tool where a choice fits and short chat questions for
free-text like file paths. `references/review-guide.md` has the full
checklist and question phrasing. **Default to what the user supplies, and
only that**: the capability profile and qualification facts are OPTIONAL —
if the user doesn't provide them, leave them out of the configuration and
the Scenario Generator runs its own Stage-1 inference. Be explicit about
the limit: an inferred profile cannot provide Stage-2 inventory evidence
(`external_integrations`, `trust_boundaries`), so if the selected risks
need those categories the projection **aborts after the mapper has run**
and the scenarios stage returns a `needs-review` request for a profile.
For a design-time run, recommend supplying a reviewed profile up front —
you may draft one from the use case, but show it in full, get approval, and
record it as agent-drafted. If the user declines a profile for a design-time
run, ask one explicit question before the mapper spends tokens: *"Without a
profile, generation may stop after the mapper if your risks need
external-integration or trust-boundary evidence. Continue anyway, or supply
a profile first?"* — and record their choice. You may OFFER to draft a profile or facts file from
what the user has told you — but if you do, show the draft in full, get
explicit user approval before it enters the run, and record it as
agent-drafted in the decision journal. Never generate these files silently.

- **Policy documents** (`.md`, `.txt`, `.pdf`, `.docx`, `.html`, …).
- **System context**: use-case description; capability profile;
  qualification facts; system identity — for a built system, the name,
  boundary, sanitized endpoint identity, and who confirmed these facts and
  when; for a proposed design, say so plainly and describe the intended
  boundary instead (there is no endpoint yet). Label synthetic examples and
  unknown values.
- **Model connections** per role as environment variables named in the run
  configuration — mapper and scenario generation for every run; artifact
  generation, target and judge additionally when the subject is built.

  **Before asking, detect what this agent already has.** Run:

  ```bash
  .venv/bin/asago-runner model-options
  ```

  It reports any endpoint/credentials/model the agent's own environment
  exposes (for example `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY`), **without
  printing secret values**, plus a conservative compatibility assessment.
  Present the detected connection to the user with the question tool as
  **one option among several** — for example:

  - *"Use the same endpoint this agent is running on — `<host>`, model
    `<model>`. It reuses the agent's credentials (usage bills to that
    account), and compatibility is not proven yet: I'll verify it with a
    labelled smoke request first."* (recommended only when its assessment is
    *likely* or *unknown*; never when *unlikely*, e.g. api.anthropic.com)
  - *"I'll give you a different endpoint, model and key."*
  - *"Use a local endpoint."*

  **Never assume the agent's endpoint.** The user chooses. If they pick a
  detected option, name that candidate's environment variables in the run
  configuration (the config records names, never values) and run the
  labelled smoke check before the pipeline. Any OpenAI-compatible model
  works, but each role has request-shape requirements (structured output,
  token/temperature parameters, completion budgets) — see "Choosing models
  per role" in `references/setup.md`.

  Copy `examples/config.example.yaml`, point it at their documents, and have
  them export the env vars it names. Ask whether concerns are missing from
  the policy; any supplement is a draft the user must verify before use.
- **Run scope**: which risks/surfaces, generation limits, target samples.
- **Optional — reviewed typed tool schemas**: if your system declares tools
  in the artifact's conversation, you may supply a JSON file with a
  top-level `tools` list (OpenAI function-tool objects) so the replayed
  calls carry your typed contract instead of schemas derived from prose.
  The artifact's own declarations must name exactly the same tools. Set it
  as `options.tools_schema_file`; it is copied into the run and validated
  at preflight.
- **Optional — retrieval models for the Policy Mapper** (ask, marked
  optional, with the question tool): the default runs local CPU models
  (downloaded automatically, nothing leaves the machine); a remote
  embedding/rerank endpoint is faster and better quality but means policy
  text is sent to that provider (it appears in the data-flow table). Only
  configure `retrieval:` if the user chooses it.

Show the user the data-flow table from preflight output: which provider
receives policies, system facts, attacks and responses. Use a labelled
synthetic/public policy unless the user has approved destinations for their
material. A shared target/judge model is acceptable for a smoke run and is
recorded as a lack of independent validation.

### 2. Run the stages

Open with the plan (see "The guided experience"), then run the stages one
at a time — narrating before, during and after each, and showing the
`status` checklist between stages. Never chain stages silently.

```bash
# new-run creates an isolated run outside the repo and prints its path:
.venv/bin/asago-runner new-run --config <config.yaml>
# → {"run_dir": "/Users/…/.asago/runs/<label>", …}
RUN=<that path>   # use the printed run_dir for every later command
.venv/bin/asago-runner preflight  $RUN      # → needs-review: input readiness
# PRESENT the request (see below); after the user answers:
.venv/bin/asago-runner respond $RUN/reviews/input-readiness.request.json \
    --decision approve --actor "<user>" --notes "<visible notes>"
.venv/bin/asago-runner preflight  $RUN --response $RUN/reviews/input-readiness.response.json
.venv/bin/asago-runner intake     $RUN      # parse receipts; conflict review if multi-doc
.venv/bin/asago-runner map        $RUN      # Policy Mapper (real CLI subprocess)
.venv/bin/asago-runner scenarios  $RUN      # projection preflight + generation
.venv/bin/asago-runner artifacts  $RUN      # eligibility + Artifact Generator + replay entries
.venv/bin/asago-runner replay-review $RUN   # → needs-review: generated test plan
# PRESENT the replay entries; after the user approves:
.venv/bin/asago-runner respond $RUN/reviews/test-plan.request.json \
    --decision approve --actor "<user>" --notes "<visible notes>"
.venv/bin/asago-runner replay-review $RUN --response $RUN/reviews/test-plan.response.json
.venv/bin/asago-runner evaluate   $RUN      # Garak, one artifact per subprocess
.venv/bin/asago-runner report     $RUN      # summary.json + offline index.html
.venv/bin/asago-runner verify-run $RUN      # model-free consistency verification
```

Stage-specific narration cues (say these in your own words):

- **preflight** — "checking your environment: the pinned components, the
  IBM risk data (fetched automatically — you don't need a clone), your
  credentials, and your input formats. No model calls happen here."
- **map** — "the mapper reads your policy and identifies risks with
  evidence. It makes many small model calls, so this can take a while."
  Afterwards: how many risks, in which taxonomies, and which of those the
  next stage can actually use (the rest are recorded gaps, not losses).
- **scenarios** — "your risks plus your system description become attack
  scenarios. Some candidates get quarantined by the component's own quality
  gates — that's normal and they're kept in the evidence."
- **artifacts** — "each admitted scenario becomes a replay conversation.
  First we check it can be faithfully represented (an attack on a
  knowledge-base feed, for example, must not be silently turned into a
  plain chat message)."
- **evaluate** — "sending the approved replay to your target and judging
  the response. One artifact at a time, under a deadline."

Notes:

- **Design-time runs (`run.subject: proposed`) stop after `scenarios`** —
  the `artifacts`, `replay-review` and `evaluate` commands refuse with a
  clear message. After `scenarios`, present the threat picture: each
  admitted scenario with its attack goal, entry point and expected unsafe
  behaviour, plus quarantined candidates and gaps — then run `report` and
  `verify-run` as usual and walk the user through `reports/index.html`,
  which carries a design-time banner. Offer to resume the full chain in a
  new run once the system is built.
- For multiple policies, `intake` returns a conflict review request. Present
  the parsed documents, ask about suspected disagreements with actual
  passages, and record the user's precedence answer. If precedence changes
  the effective input, build the reconciliation from **verbatim span
  selections** (the runner verifies slices model-free). Never paraphrase.
- `scenarios` may return a qualification-facts review: fill the generated
  facts template with real readings; absent/unknown facts must be resolved
  by the user, not invented.
- Stop at any `blocked` outcome, read the blockers, and fix the underlying
  input. Do not work around validation.

### 3. Presenting reviews

Show a **compact** summary in chat (a few lines: what's being approved,
the counts, the one or two things that need attention, and where the full
detail lives), then ask for the decision **with the question tool**
(fallback: one short chat question). For example, for the test plan:

- **Question:** "Approve the test plan for evaluation?"
- **Option "Approve":** "The exact replay batch (shown in the linked
  entries) is sent to your target: <N> conversation(s), judge criteria,
  models <target>/<judge>."
- **Option "Walk me through it first":** "I'll show each replay entry —
  messages, attack turn, derived tool schemas, judge criteria — before
  you decide."
- **Option "Reject":** "Nothing is sent. Tell me what to change."

Bind approval to the whole batch and say what was sampled versus
individually inspected. The full detail is in the request files (exact
question, material hashes, data-flow table, and for the test plan the
**exact replay entries** — messages, derived tool schemas as test
assumptions, judge criteria, target/judge models, native retry
limitations). Never paste whole request files into chat; link or summarize.

### 4. Explaining results

Open `reports/index.html` (offline, escaped content; one inline script for
stage navigation and filters, no network). The report has one tab per
pipeline stage — policy findings grouped by theme, adversarial scenarios
with their policy traces, the replay transcript, the evaluation verdict —
plus **05 Run audit**, which shows the decision journal, review gates,
stage attempts and configured models. In a design-time run the artifact and
evaluation tabs are shown disabled with the reason. Walk through themes and
counts with their separate denominators, evaluations with confidence and
reasoning, and gaps.

If you kept a transcript of this session, save it as
`$RUN/reports/conversation.md` before running `report` (or pass
`--conversation <path>`); the report includes it, escaped, in the run
audit. The transcript is rendered, not copied into `summary.json`. Be explicit about: the tested surface
(a direct chat user-turn attack is labelled as such — it is not indirect
coverage); shared model roles; inconclusive outcomes and why; what the
evidence does and does not establish. Link the native reports and the
decision journal for anything the user wants to audit.

## Failure and interruption

Stages write attempt records before invoking components, so a crash or
timeout never erases the attempt. Interrupted work leaves valid partial
evidence; a fresh attempt does not overwrite it. If the runner reports a
preflight blocker (for example the pinned Nexus data cannot be fetched or
verified), surface the remediation in the blocker text — do not pick a
different data revision yourself.

## Portability

The runner is a plain CLI: any harness or a headless caller can drive the
same stages with the same files (see `references/cli.md` for the command
contract). This skill has been demonstrated in one harness only; do not
claim untested harness support.

## Scope boundaries

The skill is **Asago**: it runs the Asago pipeline end to end. The current
evaluation endpoint is Garak (plus the offline HTML overview); the runner's
stage architecture is evaluation-agnostic, and later phases add OSCAL
export, richer reconciliation, resume/recovery and broader coverage.

The Scenario Generator runs its **taxonomy- and risk-driven workflow**
(policy-mapper risks → attack patterns → scenarios), not the STPA workflow.
If a user asks, say so plainly; STPA is a separate future extension, not a
Phase 1 mode.
Recommenders, mitigation deployment and compliance claims are out of scope.
Do not claim general policy compliance or system safety from a bounded
adversarial sample.
