01

The problem & the product

Asago connects AI policies to evidence about system behaviour. Its components existed as libraries you ran by hand — this skill turns them into a guided, reviewable, auditable operation anyone can run.

01 · Problem & Product4

What Asago does, and what the skill adds

Asago is the pipeline; the skill is how you operate it.

The Asago chain (real libraries, pinned commits)

  • Policy Mapper — policy text → taxonomy risks with evidence spans (uses IBM AI Atlas Nexus risk data)
  • Scenario Generator — risks + your system context → concrete adversarial scenarios, with native admission gates
  • Artifact Generator — admitted scenarios → validated test artifacts for an evaluation platform
  • An evaluator — currently Garak, replaying artifacts against an OpenAI-compatible Chat Completions endpoint with an LLM judge

What the skill adds around it

  • A deterministic runner (asago-runner) that invokes every component as an isolated subprocess
  • Guided intake: the agent helps you prepare the inputs the libraries expect (policies, system context, model connections)
  • Human review gates before the pipeline runs and before anything is sent to a target
  • Durable evidence: every decision, input, output and failure is retained with hashes
  • Automatic data management: the IBM Nexus risk data is fetched and verified for you

Boundary: the runner never replaces component analysis and never edits upstream source. Input adaptations are allowed and recorded; shortcuts are not.

02

Core architecture

A stage-oriented CLI drives real components in isolated subprocesses. Two locked environments, deterministic bookkeeping, and hard rules about what the runner may and may not do.

02 · Core Architecture7

The stage pipeline

Each stage is one CLI command. Exit codes make failure unambiguous: 0 completed · 4 completed-with-gaps · 2 needs-review · 3 blocked · 1 failed.

Review gates are purple/amber on purpose: the runner stops and persists a request file; nothing proceeds until a human answers. Approval binds to content hashes — change the material and the approval is stale.

02 · Core Architecture8

How components are invoked

Real CLIs, isolated subprocesses, no monkeypatching — the hard rules that keep the orchestration honest.

  • Argument arrays, not shells — every component runs via an explicit argv with absolute paths into its locked environment.
  • Environment allowlist — a child sees platform basics plus only the variables its stage needs. Stray provider keys cannot leak in or reroute a role; the Artifact Generator's .env auto-discovery finds nothing.
  • Secrets travel by env only — never in argv (visible to ps), never in evidence; captured output is redacted against the secret values before it is written.
  • Parent-enforced deadlines — a recorded wall-clock deadline, process-group kill with bounded grace; the dispatch receipt is written before the process starts, so a crash can't erase the attempt.

Two locked environments

.venv — runner + Policy Mapper + Scenario Generator + Artifact Generator + AI Atlas Nexus (pinned via a uv override, because the mapper declares a floating @main).

garak-env/ — the pinned Garak fork (trustyai-explainability/garak PR #11). Its dependency constraints conflict with the mapper's, so the environments exchange files only.

Runner-managed Nexus cache

The mapper needs a local IBM AI Atlas Nexus data clone matching the installed library revision. The runner resolves the installed commit from direct_url.json, fetches the data at exactly that commit into .cache/nexus/<commit>/, verifies every file hash against a manifest, cross-checks the installed package's bundled data, and exercises the native loader. Users never maintain a clone.

02 · Core Architecture9

The hard part: the Artifact Generator → evaluator seam

The adversarial review found the upstream defaults silently downgrade tests here. The runner's eligibility gate is the fix.

Upstream behaviour (pinned code, verified)

  • Artifacts carry no structured tool schema — tools exist only as prose lines on the system turn
  • Unknown entry-point zones silently classify as a direct user-turn attack — an indirect test can become a direct one with "full coverage" labels
  • A judge HTTP 400 crashes the evaluator; internal retries are unbounded

Runner countermeasures (all tested)

  • Model-free eligibility before any artifact model call: transport derived from the reviewed profile's structured facts; webhook ≠ chat; ambiguous → excluded, never defaulted
  • Tool schemas only from explicit declarations — declared types map to JSON Schema; untyped parameters get the loosest valid schema; never types guessed from names; undeclared called tool → excluded
  • Immutable replay entries built before review, hash-bound, rechecked immediately before dispatch
  • One artifact per subprocess with dispatch receipts; crashes/timeouts/missing detector rows → inconclusive, never a verdict

Why this matters: this seam is where a "successful" run could otherwise lie about what was tested. The runner would rather exclude and report than let an unknown surface become a direct attack.

03

Evidence, reviews & telemetry

If this process were audited, we must be able to show what we did. Evidence is ordinary files with hashes; reviews are human decisions bound to content; telemetry is operational and optional.

03 · Evidence & Reviews11

The evidence tree

Every run is a self-contained directory. Writes are atomic; the decision journal is append-only; attempts are recorded before components run, so crashes never erase history.

runs/live-smoke/ ├── run.json ← identities, config snapshot, stage/attempt records ├── inventory.json ← flat SHA-256 inventory of every retained file ├── decisions.jsonl ← append-only journal: reviews, deviations, dispositions ├── originals/ ← policies, system context, SSSOM, run config ├── derived/ ← parse receipts, reconciled inputs, span maps ├── reviews/ ← requests + responses, hash-bound ├── preflight/ ← readiness report incl. Nexus verification ├── stages/ │ ├── policy-mapper/<attempt>/ ← native extraction + receipts │ ├── scenario-generator/<attempt>/ ← native manifest v3, inventory, quarantine │ ├── artifact-generator/<attempt>/ ← artifacts, validations, replay entries │ └── garak/<attempt>/<dispatch>/ ← conversation, dispatch receipts, native report └── reports/ ← summary.json + offline index.html
  • States stay distinct: a risk match is not a finding; an admitted scenario is not an executable artifact; skip may coexist with ok=true and stays skipped; inconclusive is not a pass
  • Exclusions are visible: unsupported taxonomies, quarantined candidates, partial coverage and inconclusive dispatches all carry reasons and links
  • Secrets never appear: verify-run scans the whole tree for configured key values
  • verify-run re-derives consistency model-free: admission receipts, parent hashes, dispatch↔attempt correlation, detector results, review bindings — 17 checks on the live run
03 · Evidence & Reviews12

Review gates and telemetry separation

Humans decide at three boundaries; the Collector observes operations but no audit information depends on it.

Three review gates

  • Input readiness (before the pipeline): documents, system identity, the data-flow table — which provider sees your policy text — scope and models
  • Policy conflict (multi-document): suspected disagreements presented with actual passages; precedence via verbatim span reconciliation with a machine-checked span map
  • Test plan (before evaluation): the exact replay batch — messages, derived tool schemas (labelled test assumptions), judge criteria, target/judge models, retry limitations

Reviews are files: the runner persists a request and returns needs-review — no live waiting. Approval is never inferred from elapsed time, and a material change invalidates it.

Telemetry (OpenTelemetry)

  • Run/stage/attempt spans via standard OTLP env config — your Collector, your backend; none is provisioned
  • Identifiers, statuses, timings and bounded counts only — never prompts, policies, attacks or responses
  • Export failure is a recorded warning; evidence is unaffected
  • Demonstrated against a local test receiver in the test suite

The separation is the point: an auditor needs files, not traces. An operator wants traces, not audit noise. Each gets its own channel, and neither can fake the other.

04 · The Live Run15

Model contracts discovered the hard way

The gateway's validators and the components' hardcoded limits constrain which model can run which stage. All found by experiment, all recorded in the compatibility record and decision journal.

StageModel usedWhy (measured fact)
Mappera fast gateway modelCompleted in ~13 min (393 calls). a reasoning-heavy gateway model rerun hit the 60-min stage deadline near completion — ~4–5× slower; the completed attempt was kept.
Scenariosa concise gateway modela reasoning-heavy gateway model's drafts exceed the component's hardcoded 4096-token caps; a fast gateway model is rejected by the gateway's strict-schema validator (maxProperties); all Gemini models reject the behavior schema. a concise gateway model accepts it and fits (1488 tokens on a maximal probe).
Artifactsa reasoning-heavy gateway modelAccepts the generator's hardcoded temperature=0.2 (a fast gateway model and a fast gateway model accept only temperature=1).
Target + judgea reasoning-heavy gateway modelYour free-model default; accepts every request shape. Shared target/judge — flagged, not hidden.

Every deviation is a journal record with the user instruction or measured failure that forced it, the alternatives tried, and the scope affected. Rerunning any single stage on a different model is cheap if you'd prefer another combination.

05

What's next

Phase 1 deliberately stopped at a working, honest chain. Phase 2 builds the assessment workflow on top of retained evidence — starting with OSCAL.

05 · What's Next17

Phase 2 (deliberately deferred)

Phase 1 retained everything Phase 2 needs — that was the design constraint. Nothing has to be re-run to export later.

OSCAL export (first priority)

  • Assessment Plan / SSP / Assessment Results derived from retained evidence
  • Native files stay as linked resources with hashes; the decision journal is detailed source evidence
  • Inconclusive/skipped work stays observations and gaps — never forced into binary findings

Richer review & recovery

  • Larger-scale conflict analysis, clause-level precedence, review queues
  • Config fingerprints, dependency-aware invalidation, cross-stage resume

Broader coverage & observability

  • More input formats, endpoint configurations, harnesses — tested, then claimed
  • Tool-return live coverage once a reviewed carrier and endpoint support are established (the offline adapter path already works)
  • Client-level model-call instrumentation without source edits

Out of scope entirely: recommenders, mitigation deployment, compliance claims from bounded samples, and any claim of general safety.

Closing18

Key takeaways

  • The chain works, end to end, for real: policy documents → mapper → scenarios → artifact → Garak → judged result, with the synthetic policy producing attack_not_demonstrated (judge 0/100) and every number accounted.
  • The runner orchestrates; it never analyzes. Real components at pinned commits, isolated subprocesses, env allowlists, no source edits, no monkeypatching.
  • Evidence is files with hashes; telemetry is optional OTel. An auditor never needs the Collector; verify-run re-derives consistency model-free (17/17 on the live run).
  • Humans decide at three gates — input readiness, policy conflicts, and the exact replay batch before anything touches a target. Approvals bind to hashes; changes invalidate them.
  • Honesty is structural, not aspirational: unsupported taxonomies, quarantined scenarios, partial coverage, inconclusive dispatches and shared-model judges are all recorded and surfaced, never smoothed over.
  • Model contracts are a real constraint: the compatibility record documents which gateway models can run which stage and why — measured, not assumed.
